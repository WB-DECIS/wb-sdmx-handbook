# World Bank SDMX Handbook

A Quarto book covering SDMX dataflow creation, data pipelines, and VTL at the World Bank.
Chapters live in the `*.qmd` files at the repository root and are ordered by `_quarto.yml`.

## Local preview

```bash
quarto preview     # live-reloading preview
quarto render      # one-off build into _book/
```

The book uses only the `markdown` engine — no code chunks are executed at render time, so
neither Python nor R is needed to build it. `requirements.txt` exists for running the
pipeline examples locally, not for rendering.

## Deployment (git-backed Posit Connect)

The published site is a **git-backed** Posit Connect deployment. Connect polls this
repository (every 15 minutes by default), and when the tracked branch moves it pulls the
new commit and renders the book itself. Nothing is pushed from a laptop, and the rendered
`_book/` output is never committed.

The contract between the repository and Connect is `manifest.json`. It declares the
content type (`quarto-static` / `site`), the Quarto version to render with, and the
**explicit list of files** Connect should pull into the build, each with an MD5 checksum.

### The one rule

**Any time you add, delete, or rename a file, regenerate `manifest.json` and commit it in
the same commit.** Connect builds from the file list in the manifest, not from whatever
happens to be in the repository — a new chapter or image that is not in the manifest will
not reach the server, and a manifest entry for a file that is not committed to git will
break the build.

Editing the contents of an existing file only makes its checksum stale, which is harmless
for the build but leaves the manifest lying about the state of the repository. Regenerate
it anyway so drift does not accumulate.

### Regenerating the manifest

`manifest.json` is generated by [`rsconnect-python`](https://docs.posit.co/rsconnect-python/commands/write-manifest/),
not by the `quarto` CLI. Install it once:

```bash
uv pip install rsconnect-python      # or: pip install rsconnect-python
```

Then, from the repository root:

```bash
rsconnect write-manifest quarto . --overwrite -x .venv -x .quarto -x _book -x .positai -x .Rproj.user -x .Rhistory
```

The `-x` exclusions matter. `rsconnect` walks the working directory and does **not** read
`.gitignore`, so without them it happily records local-only directories — a virtual
environment, Quarto's build cache, editor state — as files Connect is expected to find in
the repository. It cannot, and the deployment fails.

Review the diff before committing:

```bash
git diff manifest.json
```

Every path that appears should be a file that is committed to git; every file the book
needs to render should appear.

### Deploying

```bash
git add manifest.json <the files you changed>
git commit -m "..."
git push
```

Then wait for Connect's next poll, or open the content's **Settings → Git** panel in
Connect and trigger an update immediately. The same panel shows the build log when a
render fails.

### Notes and gotchas

- **Quarto version.** The manifest pins `quarto.version` to whatever was installed locally
  when it was generated (currently `1.9.36`). Connect renders with a Quarto it has
  installed; if the server has nothing compatible, the build fails with a version error.
  Check `quarto --version` locally before regenerating if the pin changes unexpectedly.
- **`.positai/`.** This directory is local Posit AI state and is not committed, so it is
  excluded above. An earlier manifest listed `.positai/settings.json`, which would have
  failed on a clean clone.
- **Git LFS is not supported** by Connect's git-backed publishing. Keep large assets as
  ordinary git objects (`docs/` currently holds a few XML/XLSM files this way).
- **Only the tracked branch deploys.** Connect watches one branch — currently `master`.
  Work on another branch changes nothing on the server until it is merged.
